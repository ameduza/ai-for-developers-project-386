# Guest booking access is by unauthenticated link

The system has no auth (see `CONTEXT.md`), yet the API Contract exposes `GET /bookings/{id}` and `DELETE /bookings/{id}` for Guest use. We decided the frontend exposes a durable `/bookings/:id` confirmation page as the Guest's only way to view or cancel a Booking later — knowledge of the Booking id (for example, via a bookmarked or emailed link) is the sole gate; there is no additional secret or login. The alternative (omitting a cancel UI entirely) was rejected because the API Contract already defines the endpoint and the frontend should match its ceiling. This means anyone who obtains a Booking's URL can cancel it; revisiting this later to add a real secret or auth would require reworking the Guest flow.
