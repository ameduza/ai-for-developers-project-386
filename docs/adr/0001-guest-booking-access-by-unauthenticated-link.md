# Guest booking access is by unauthenticated link

The system has no auth (see `CONTEXT.md`), yet the API Contract exposes `GET /bookings/{id}` and `DELETE /bookings/{id}` for guest use. We decided the frontend exposes a durable `/bookings/:id` confirmation page as the guest's only way to view or cancel a Booking later — knowledge of the booking id (e.g. via a bookmarked/emailed link) is the sole gate, there is no additional secret or login. The alternative (omitting a cancel UI entirely) was rejected because the contract already defines the endpoint and the frontend should match its ceiling. This means anyone who obtains a booking's URL can cancel it; revisiting this later to add a real secret or auth would require reworking the guest flow.
